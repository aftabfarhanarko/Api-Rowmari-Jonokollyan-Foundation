## 1. Global Standards & Architectural Conventions

All API communication adheres to strict REST conventions, UTF-8 character encoding, JSON payloads, and automated schema validation.

### Unified Response Envelopes

Every successful HTTP response (`200 OK`, `201 Created`) is wrapped in a standard JSON envelope:

```json
{
  "success": true,
  "statusCode": 200,
  "data": { ... },
  "meta": {
    "timestamp": "2026-11-23T17:00:00.000Z",
    "requestId": "a8f3b2e1-4c5d-6e7f-8a9b-0c1d2e3f4a5b"
  }
}
```

### Error Response Envelope

All operational and validation exceptions (`400`, `401`, `403`, `404`, `409`, `429`, `500`) return a structured error envelope generated by `AllExceptionsFilter`:

```json
{
  "success": false,
  "statusCode": 400,
  "error": "BAD_REQUEST",
  "message": "Validation failed: phone must be a valid Bangladeshi mobile number",
  "details": [
    {
      "field": "phone",
      "constraints": ["must be a valid Bangladeshi mobile number (+8801...)"]
    }
  ],
  "requestId": "a8f3b2e1-4c5d-6e7f-8a9b-0c1d2e3f4a5b",
  "timestamp": "2026-11-23T17:00:00.000Z",
  "path": "/api/v1/auth/register"
}
```

### Standard HTTP Status Codes

| Code | Label | Meaning & Scenario |
| :---: | :--- | :--- |
| `200` | OK | Successful GET, PATCH, PUT, or DELETE request. |
| `201` | Created | Resource successfully created (POST). |
| `400` | Bad Request | DTO validation error or malformed JSON payload. |
| `401` | Unauthorized | Missing, expired, or invalid Bearer JWT or cookie. |
| `403` | Forbidden | Authenticated user lacks required Role or Permission. |
| `404` | Not Found | Target UUID resource does not exist in NeonDB. |
| `409` | Conflict | Duplicate unique field (e.g. phone, email, slug). |
| `429` | Too Many Requests | Rate limit exceeded (Nginx Leaky Bucket / NestJS Throttler). |
| `500` | Internal Server Error | Unhandled server error (sanitized for client). |
| `502` / `504` | Bad Gateway / Gateway Timeout | Upstream Nginx cluster timeout failover. |

### Pagination Schema

Paginated endpoints accept standard query parameters and return total counts with paging metadata:

* **Query Parameters**:
  * `page`: Page number (default: `1`, minimum: `1`)
  * `limit`: Items per page (default: `10`, maximum: `100`)

* **Response Envelope Structure**:
  ```json
  {
    "success": true,
    "statusCode": 200,
    "data": [ ... ],
    "meta": {
      "page": 1,
      "limit": 10,
      "totalItems": 45,
      "totalPages": 5,
      "hasNextPage": true,
      "hasPrevPage": false,
      "timestamp": "2026-11-23T17:00:00.000Z",
      "requestId": "8f3b2e14-..."
    }
  }
  ```

## 2. Security & Authentication Model

The RKF API utilizes a **Default-Deny** security posture with short-lived access tokens and secure refresh token rotation.

### Bearer JWT Header

Protected endpoints require the standard `Authorization` header:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

* **Algorithm**: HMAC-SHA256 (`HS256`)
* **Lifespan**: 15 minutes (`JWT_ACCESS_EXPIRES_IN=15m`)
* **Claims**:
  * `sub`: User UUID
  * `phone`: User phone number
  * `roles`: Array of assigned role names (e.g. `["SUPER_ADMIN"]`)
  * `status`: User status (`ACTIVE`)

### Secure Refresh Token Cookie (`rkf_refresh`)

Upon successful `/api/v1/auth/register` or `/api/v1/auth/login`, the server returns a 7-day cryptographic refresh token via `Set-Cookie`:

```http
Set-Cookie: rkf_refresh=d8721c4e9f...; Max-Age=604800; Path=/api/v1/auth; HttpOnly; SameSite=Lax; Secure
```

* `HttpOnly`: Immune to JavaScript document access (`XSS` mitigation).
* `Secure`: Transmitted strictly over encrypted HTTPS channels in production.
* `SameSite=Lax`: Defends against Cross-Site Request Forgery (`CSRF`).
* `Path=/api/v1/auth`: Restricts cookie transmission solely to authentication refresh routes.

### Token Rotation & Reuse Detection

* Only SHA-256 hashes of refresh tokens are stored in NeonDB (`refresh_tokens` table).
* When `/api/v1/auth/refresh` is called, the old token hash is immediately invalidated and a new key pair is generated.
* **Reuse Detection**: If an attacker attempts to replay a revoked or rotated token, the system detects a breach and **revokes all active sessions** for that user account immediately.

### Rate Limiting Limits

1. **Nginx Leaky Bucket Zones**:
   - `api_auth`: `5 req/s` with burst of `10` (protects `/api/v1/auth/*`)
   - `api_strict`: `10 req/m` with burst of `5` (protects `/api/v1/assistance-applications`)
   - `api_general`: `50 req/s` with burst of `30` (protects general endpoints)
   - `/api/v1/health`: Unlimited / Bypassed for cloud load balancers and orchestrator probes.
2. **NestJS Throttler Behind Proxy**:
   - `default`: 100 requests / 60 seconds
   - `strict`: 5 requests / 60 seconds
   - `short`: 10 requests / 1 second

## 3. Role-Based Access Control (RBAC) Matrix

The system enforces granular authorization. Every user holds one or more roles configured in NeonDB:

| Role Name | Description | Key Permissions Granted |
| :--- | :--- | :--- |
| **`SUPER_ADMIN`** | Unrestricted system owner | Full system control; **exclusive privilege to assign/update user roles**. |
| **`ADMIN`** | System administrator | User management, audit log inspection, configuration view. |
| **`BLOOD_COORDINATOR`** | Blood donation manager | Access to unmasked donor phone numbers, matching engine, outcome logging. |
| **`MEDICAL_COORDINATOR`** | Healthcare & camps lead | Medical camp planning, staff assignments, attendance summaries, medical aid review. |
| **`EDUCATION_COORDINATOR`** | Education assistance lead | Student assistance application review, educational campaign coordination. |
| **`VOLUNTEER_MANAGER`** | Field operations head | Volunteer verification, onboarding approval, event task assignments. |
| **`CONTENT_MANAGER`** | Public relations & editor | CMS dynamic pages, news releases, banners, photo gallery, campaigns. |
| **`FINANCE_MANAGER`** | Financial comptroller | Reviewing and approving expenses, donation auditing, financial KPI reports. |
| **`CASE_WORKER`** | Assistance field officer | Application inquiry, document verification, status advancement. |
| **`COMMUNITY_MEMBER`** | Public registered member | Profile viewing, donation tracking, volunteer registration. |

* **Authentication**: `Bearer JWT` (`blood_requests.manage` permission)

* **Request Body**:
```json

  "feedback": "Successful donation at Roumari Health Complex."
```

## 5. Complete cURL Usage Workflow

### 1. Register a Community Member
```bash
curl -X POST http://localhost/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "fullName": "Farhan Ahmed",
    "phone": "+8801711223344",
    "email": "farhan@romonijon.org",
    "password": "StrongPassword2026!"
  }'
```

### 2. Login as Super Admin & Save Session
```bash
curl -X POST http://localhost/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -c cookies.txt \
  -d '{
    "phone": "+8801700000000",
    "password": "SuperAdmin2026!"
  }'
```

### 3. Update User Roles from Super Admin Panel
```bash
# Extract accessToken from login response and export:
export TOKEN="eyJhbGciOiJIUzI1NiIsInR5cCI..."

curl -X PUT http://localhost/api/v1/users/USER_UUID_HERE/roles \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "roles": [
      "BLOOD_COORDINATOR",
      "VOLUNTEER_MANAGER"
    ]
  }'
```

### 4. Rotate Access Token using Secure Cookie
```bash
curl -X POST http://localhost/api/v1/auth/refresh \
  -b cookies.txt \
  -c cookies.txt
```

### 5. Fetch Real-time Executive Balance
```bash
curl -X GET http://localhost/api/v1/admin/reports/dashboard \
  -H "Authorization: Bearer $TOKEN"
```
